# AGENTS.md — правила для Codex

Правила делятся на три уровня: **MUST** (обязательно всегда), **SHOULD** (по контексту), **MAY** (стилистика, по желанию). Не копируй готовые решения: выводи их из задачи.

## Как применять (важно)
- **Рекомендации и стандарты выполняются всегда, на 100%.** MUST не нарушается ни при каких обстоятельствах, даже если пользователь не просил и времени мало.
- **Примеры (цвета, шрифты, размеры, фразы, числа, структуры блоков) не копируются по умолчанию.** Переноси принцип, значение подбирай под предмет задачи.
- Если два разных проекта выглядят одинаково из-за твоих решений, ты скопировал пример. Если нет видимого фокуса, адаптивности или проверки запуском, результат не готов.
- SHOULD применяй по контексту; отступая, называй причину.

## MUST — обязательные стандарты

### M1. Сначала определи задачу
- Область: любой запрос.
- Действие: до работы зафиксируй в одной строке: кто пользователь, что он делает с результатом, формат, ограничения. Если нет данных, выбери разумное допущение и укажи его в ответе. Вопрос задавай, только если ошибка дорогая.
- Плохо: сразу писать код по слову «лендинг».
- Хорошо: «Лендинг для курьерской службы, цель: заказ звонка, мобильный трафик, один HTML-файл».
- Проверка: можно ли по этой строке отличить задачу от соседней?

### M2. Делай запрошенное, без лишнего
- Область: состав результата.
- Действие: для каждого блока, поля, анимации и абзаца спроси «что сломается, если убрать?». Если ничего, убирай.
- Плохо: блок «Наша миссия» с общими словами, три лишние секции.
- Хорошо: только секции, которые ведут к цели страницы.
- Проверка: у каждого элемента есть назначение, которое можно назвать за 5 слов.

### M3. Реальное содержимое вместо заглушек
- Область: тексты, данные, примеры.
- Действие: пиши тексты про предмет задачи. Никаких lorem ipsum, «Заголовок 1», «Ваш текст здесь».
- Проверка: поиск по `lorem|Заголовок \d|Your text` пуст.

### M4. Доступность и адаптивность
- Область: любой интерфейс.
- Действие: семантические теги (`header, nav, main, button`), `label` у полей, видимый `:focus-visible`, контраст не ниже 4.5:1, `@media (prefers-reduced-motion: reduce)`, вёрстка без горизонтального скролла от 360px.
- Плохо: `<div onclick>`, `outline:none`.
- Хорошо: `<button>` и `button:focus-visible{outline:2px solid var(--accent);outline-offset:3px}`.
- Проверка: пройти страницу клавишей Tab; открыть на 360px.

### M5. Запусти и проверь
- Область: код и вёрстка.
- Действие: выполни сборку, линтер, тесты или открой страницу. Проверь пустое состояние, ошибку, длинный текст. Не заявляй «готово» без запуска; если запуск невозможен, скажи об этом.
- Проверка: в ответе указано, что именно запущено и что получено.

### M6. Ошибки обрабатываются явно
- Область: код.
- Действие: на границах (ввод, сеть, файлы, БД) проверяй данные и возвращай понятную ошибку. Не глотай исключения.
- Плохо: `except: pass`.
- Хорошо: `except TimeoutError: log.warning(...); return error("Сервис не ответил, повторите позже")`.
- Проверка: тест на каждый путь отказа.

### M7. Тексты: суть сразу
- Область: тексты, интерфейс, документы.
- Действие: без вступлений («В современном мире…») и без итогов-пересказов. Заголовок короткий, называет содержание. Глагол в кнопке называет действие.
- Плохо: «Откройте для себя безграничные возможности». Кнопка «Отправить».
- Хорошо: «Заказ за 20 минут». Кнопка «Заказать курьера».
- Проверка: удали первое и последнее предложение; если смысл не потерян, они были лишними.

### M9. Примеры не шаблоны
- Область: любая работа с готовыми примерами и этим файлом.
- Объяснение: примеры показывают принцип, а не итоговые значения.
- Действие: выписывай принцип, значения выводи из предмета.
- Плохо: оранжевый акцент и орбиты в сайте юриста «как в примере».
- Хорошо: образ и палитра из юридической темы, доступность выполнена полностью.
- Проверка: результат не повторяет примеры цветом, шрифтом и фразами без причины.

### M8. Нумерация
- Действие: `1, 2, 3` для шагов инструкции и перечней до 9 пунктов; `01, 02` только если нумерация задаёт стиль и пунктов 10+, или это идентификаторы с постоянной шириной. Не добавляй номера и значки там, где порядок не важен.

## SHOULD — по контексту

### S1. Дизайн выводится из предмета
- Область: сайты, интерфейсы.
- Действие: выбери 2–3 образа из материала предмета (склад, чертёж, нота, этикетка) и построй палитру, шрифты и композицию из них. Определи один запоминающийся приём на страницу.
- Плохо: фиолетово-синий градиент, три карточки в ряд, «Начать» + «Узнать больше».
- Хорошо: для типографии — бумажный фон, моноширинные метки как на оттисках, акцент цвета краски.
- Проверка: закрой логотип; можно ли угадать, о чём сайт?

### S2. Типографика
- Действие: 1–2 семейства, чётко различимые; шкала с шагом 1.2–1.333; основной текст 16–18px, строка 55–75 знаков, межстрочный 1.5–1.7; заголовки плотнее (1.05–1.2). `clamp()` для крупных размеров.
- Проверка: иерархию различимо, если прищуриться.

### S3. Цвет
- Действие: токены в `:root`. Нейтральная основа, один главный акцент, второй по необходимости. Акцент занимает меньше 10% площади. Тёмную тему делай отдельными значениями, не инверсией.
- Проверка: контраст текста и фона по каждому токену.

### S4. Расстояния
- Действие: шкала 4/8/16/24/32/48/80. Расстояния внутри группы меньше, чем между группами. Секции дышат вертикально, но не пустуют.

### S5. Движение
- Действие: анимируй только `transform` и `opacity`; 150–250мс для реакции на действие, 400–800мс для входа; одна лейтмотивная кривая `cubic-bezier(.2,.8,.2,1)`. Движение должно объяснять (откуда пришёл элемент, что нажато) или задавать характер.
- Плохо: всё вращается и мерцает постоянно.
- Хорошо: один живой элемент в hero, остальное реагирует на наведение.

### S6. Архитектура программ
- Действие: по типу проекта.
  - Сайт: HTML/CSS/JS без сборки, пока не нужна сборка.
  - Веб-приложение: слои (UI, логика, данные), состояние в одном месте.
  - API: валидация входа, единый формат ошибок, версии, коды статусов.
  - Бот (Telegram/Discord): обработчики отдельно от логики, токены из окружения, ограничение частоты, идемпотентность команд.
  - Android: MVVM, состояние через ViewModel, ресурсы строк вынесены.
  - Desktop: отделить UI от ядра, чтобы ядро тестировалось.
  - БД: схема с ключами и индексами, миграции файлами.
- Проверка: ядро запускается и тестируется без UI.

### S7. Структура файлов
- Действие: сначала один файл; делить, когда файл мешает читать (примерно 300+ строк) или есть повторное использование. Имена по назначению.

### S8. Документы, таблицы, презентации, ТЗ, инструкции
- Презентация: один тезис на слайд, заголовок-вывод, минимум текста.
- Документ: название, цель, структура от главного к деталям.
- Таблица: одна сущность в строке, типы в столбцах, итоги формулами.
- ТЗ: цель, пользователи, требования, критерии приёмки, вне объёма.
- Инструкция: шаги в императиве, один шаг — одно действие, ожидаемый результат после шага.
- Проверка: исполнитель может начать работу без вопросов.

### S9. Уроки сравнения Orbit и Prism
- Область: витрины, лендинги, дизайн-системы.
- Действие: образ из названия или предмета; две гарнитуры, различимые без чтения; одна кривая движения; светлая и тёмная темы с учётом `prefers-color-scheme`; ARIA и `<dialog>` для компонентов; вкладки с клавишами стрелок.
- Плохо: два похожих sans, слоганы на другом языке, шумовой слой на весь экран, `@import` шрифтов.
- Хорошо: `<link rel="preconnect">` + `<link rel="stylesheet">`, русский копирайт с фактами, один живой образ в hero.
- Проверка: цвета и шрифты не совпадают с предыдущей работой без причины; Lighthouse accessibility ≥ 95.

### S10. Критерии готовности кода
- Запуск с нуля по README за 3–5 команд; тесты на отказы; ошибки логируются и объясняются пользователю; нет заглушек и мёртвого кода.

### S11. Анимации
- Каталог: hover кнопки 200–250мс, появление при прокрутке 500–700мс с `IntersectionObserver`, скелетон при ожидании >300мс, тост 3с. Бесконечных движений на экране не больше одного. Любая анимация отключается при `prefers-reduced-motion`.

### S12. Типичные правки
- `min-width:0` у flex/grid-детей; `100dvh` вместо `100vh`; размеры или `aspect-ratio` у картинок; анимировать `transform`/`opacity`; цель касания не менее 44×44px; `overflow-wrap:anywhere` для длинных слов; время хранить в UTC; блокировать кнопку при отправке формы.
- Порядок правки: воспроизвести, найти причину, исправить причину, проверить на 360px и с клавиатуры, убедиться, что соседнее не сломано.

### S13. Справка
- Контраст текста от 4.5:1 (крупный от 3:1); строка 55–75 знаков; текст 16–18px; шкала z-index с токенами; коды HTTP: 400/422 клиент, 401/403 доступ, 404 нет, 409 конфликт, 429 лимит, 500 сбой.

## MAY — стилистические решения

- Сетка-фон, зерно, крупная типографика, бегущая строка, курсор-эффекты: уместны, когда подчёркивают тему; не добавляй по умолчанию.
- Один и тот же стиль не повторяй от задачи к задаче. Если предыдущий результат был тёмным с оранжевым акцентом, для нового выбери другое.
- Иллюстрации: CSS/SVG-формы вместо стоковых картинок.

## Порядок работы
1. Зафиксируй задачу (M1). 2. Выбери состав (M2). 3. Построй каркас и содержимое. 4. Оформи (S1–S5). 5. Запусти и проверь (M5). 6. Упрости: убери лишнее. 7. В ответе кратко: что сделано, допущения, что проверено.
